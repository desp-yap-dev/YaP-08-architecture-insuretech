# Задание 3. Переход на Event-Driven архитектуру

## Текущее решение

Сервисы core-app и ins-comp-settlement получают данные о доступных продуктах через REST API сервиса ins-product-aggregator. В момент вызова он:
- запрашивает информацию из всех страховых компаний (сейчас их пять),
- агрегирует её в единый список,
- возвращает этот список в рамках того же синхронного запроса.

Чтобы ускорить работу сервисов, при изначальном проектировании команда решила хранить локальные реплики данных о продуктах и тарифах в сервисах core-app и ins-comp-settlement.

Сервис core-app осуществляет запрос к ins-product-aggregator раз в 15 минут, а ins-comp-settlement — раз в сутки (ночью), при формировании реестра оформленных страховок. Иногда команда сталкивается с ошибками взаимодействия между этими сервисами. Они связаны с задержками ответов или ошибками при взаимодействии с API страховых компаний.
Дополнительно сервис ins-comp-settlement раз в сутки осуществляет запрос в core-app по REST API для получения всех оформленных за день страховок. Эти данные он использует. 

В ближайшее время InsureTech планирует подписать агентское соглашение ещё с пятью страховыми компаниями

## Проблемы текущего решения

ins-product-aggregator синхронно обращается в 5 страховых компаний, в ближайшее время их станет 10. Присутствуют следующие риски: 
- возможность каскадного сбоя: не получили ответ от одной СК, но ввиду синхронности не вернется ответ целиком
- возможный таймаут: суммарное время ожидания ответа ото всех СК может превысить допустимый таймаут
- проблема масштабирования: каждое увеличение количества СК будет приводить к увеличению времени ответа
- неизвестно, есть ли механизм retry 
- непонятно, как согласовываются данные реплик в core-app и ins-comp-settlement
- синхронное взаимодействие между ins-comp-settlement и core-app чревато ошибками: в случае не получения данных возможно нарушение функционирования сервиса ins-comp-settlement (указано, что ему нужны эти данные)

## Предлагаемое решение

### 1. Рефакторинг ins-product-aggregator

Вместо обращения в СК по запросу настраиваем scheduler, который по расписанию будет обращаться к СК (интервал можно оставить тем же - раз в 15 мин), после получения ответа агрегировать данные и обновлять их в своем хранилище (БД либо кэш). При наличии обновления сервис будет публиковать событие в брокер сообщений через Transactional Outbox. 
Текущее REST API можно оставить, но данные возвращать не путем обращения во все СК, а из локального хранилища.

### 2. Рефакторинг core-app

Вместо осуществления запроса раз в 15 мин к ins-product-aggregator реализуем подписку на топик в брокере, куда ins-product-aggregator публикует события об обновлениях. При получении такого обновления - обновляем лкокальную реплику. 
Кроме того, настраиваем брокер сообщений между core-app и ins-comp-settlement: при каждом успешно оформленном полисе сервис core-app публикует событие об этом через Transactional Outbox. 

### 3. Рефакторинг ins-comp-settlement

Вместо ночного обращения к ins-product-aggregator подписываемся на топик в брокере, куда ins-product-aggregator публикует события об обновлениях. 
Вместо обращения раз в сутки к core-app по REST API подписываеся на топик в брокере, куда core-app публикует события о выданных полисах.

## Плюсы решения

Разорваны синхронные связи между сервисами, теперь сбой в одном из них не приведет к сбоям в другом. 
Упрощена возможность горизонтального масштабирования. Добавление новых СК не приводит к увеличению времени ответа. 

## Обоснование необходимости использования Transactional Outbox

Данный паттерн в данном случае поможет решить проблему двойной записи: в случае, если сервис получил обновления от СК, записал в свое хранилище, но "упала" запись в брокер, данное событие может быть потеряно. При использовании же паттерна гарантируем, что события не будут потеряны, а бизнес-логика не нарушена.
